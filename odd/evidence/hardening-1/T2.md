## Design (as decided in S2)

- `RecipientAccess.pairKeyOf`: the normalized typed postal code (whitespace
  removed, upper case) longer than `Destination_Postal_Code__c`
  (`Shipment__c.Destination_Postal_Code__c.getDescribe().getLength()`, 10) is
  hashed as the fixed token `MALFORMED-POSTAL-CODE`. That token is 21
  characters long, so no value of 10 or fewer, which keeps its own pair, can
  share it. The SHA-256 is still computed on every path, so the work is the
  same; `DeliveryAccessCode.matches` still runs once.
- `postalMatches`: `storedPostalCode != null && storedPostalCode.equals(normalizedPostalCode(postalCode))`.
  `.equals` compares exactly, while Apex `==` ignores case and folds U+212A to
  "K" (proven red below). I did not use the key-equality alternative: a stored
  code whose normalized form grows past 10 characters (for example "ß" upper
  cased to "SS") would then match every over-long typed value.
- `RecipientAccessGuardPurge`: `with sharing`, implements `Schedulable` and
  `Database.Batchable<SObject>`. `start` selects rows with
  `(Locked_Until__c = null OR Locked_Until__c <= now) AND LastModifiedDate < now - 1 day`.
  `execute` re-reads its scope `FOR UPDATE` with the same conditions and
  deletes only those rows (`Database.delete(rows, false, AccessLevel.SYSTEM_MODE)`),
  so a row a guest locked or touched after `start` is kept. A
  `// SECURITY-JUSTIFICATION:` comment covers the system mode: no user holds
  object permissions on the guard. `scheduleDaily()` returns the existing
  CronTrigger named `RecipientAccessGuardPurge daily` if there is one, and
  otherwise schedules `0 0 3 * * ?`.
- `scripts/setup/schedule-guard-purge.sh <alias>`: counts the job, runs
  `scheduleDaily()` from a temporary .apex file, then requires exactly one
  CronTrigger with that name.

## Security notes (sf-security-code-review)

- P11: RecipientAccessGuardPurge is `with sharing`. Its system-mode query and
  delete carry a SECURITY-JUSTIFICATION, pending owner approval as in T1. It
  has no guest entry point and no caller input; `scheduleDaily` needs
  anonymous Apex or class access, and the guest has none.
- The purge deletes only rows its running user can see. The script documents
  "run as an admin". If a user without View All Data scheduled it, rows they
  cannot see would stay. That is safe (no wrong delete) but not bounded.
- Hard rules: no key or hash is returned or logged; the purge has no debug
  output. No object permission was given to anyone.
- Governor limits: the batch runs 200 rows per chunk with 1 SOQL and 1 DML per
  chunk, and `start` uses a QueryLocator (up to 50M rows). `pairKeyOf` normalizes
  a typed value of any length with `replaceAll`. A very long payload costs
  regex CPU before it is classified as malformed; this is unchanged from T1.
