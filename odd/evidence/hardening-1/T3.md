## H2: does the setting reach Experience Cloud customer logins?

Outcome: decided by the main session on 2026-11-18 (task document H2, c7b2386): proceed. Basis recorded there: the org-level "Require MFA for all direct UI logins" applies to internal users' direct logins; MFA for Experience Cloud external users is a separate opt-in through the "Multi-Factor Authentication for User Interface Logins" user permission (`PermissionsForceTwoFactor`). The customer profile must not hold it, and the check script now asserts that.

What T3 could and could not read (first run, before any deploy):
- Could not read: help.salesforce.com articles (Enable MFA for direct UI logins, Exclude Exempt Users from MFA, MFA FAQ 000388806). They return only the JavaScript application shell to curl. developer.salesforce.com and admin.salesforce.com returned an error page. A crawler user agent was refused by the auto-mode classifier, and no other way around it was tried. T3 therefore stopped with no deploy and no commit, and reported.
- Read (PDFs from resources.docs.salesforce.com):
  - Summer '22 release notes, "Enable Multi-Factor Authentication for Your Entire Org": the setting is on Setup > Identity Verification. The exempt cases admins must waive themselves are test automation, RPA, PIV/CAC, and trusted device plus network. External or site users are not listed.
  - Winter '23 and Spring '23 release notes: Chatter Free and Chatter External users are excluded automatically when the setting is on.
  - Winter '23, Spring '23 and Winter '24 release notes (auto-enablement release update): the release update turns this setting on for every production org.
  - Summer '24 release notes: "Each time a user logs in directly to your production org with their Salesforce username and password, they must also provide an MFA verification method."
  - Salesforce Security Guide (v258) and the Experience Cloud guide (v240, v246, v258): neither scopes the setting to site logins.
  - None of these sources names Experience Cloud or Site.login explicitly. They lean towards site logins not being covered, which is the basis the main session decided on.
- Org facts at the time: 4 active Customer Community users (profile "RutaCargo Customer", UserType CspLitePortal), 2 System Administrators, 1 API-only integration user (EntregaYa, client credentials), 1 guest user. `PermissionsForceTwoFactor` was false on the "RutaCargo Customer" profile, on `RutaCargo_Customer`, and on every profile whose UserType is not Standard. 0 active users with a UserType other than Standard held it.

Who is affected: both System Administrators register a verification method at their next direct UI login. The CLI's existing scratch-org authorization and `sf org open` are not direct UI logins; a new `sf org login web` goes through the login page.

Reversal: set the value to `false` in the file and deploy it the same way (proved by the mutation below).

Owner confirmation (pending, human test): log in once as a seeded customer on the live RutaCargo site and confirm that no MFA prompt appears; if MFA is demanded, deploy the setting as false and reopen SEC-003. Result: _not yet recorded_.

## Governor and operational notes
- The script makes one metadata retrieve and five SOQL queries per run, all read-only. The retrieve goes to a `mktemp` folder that is removed on exit.
- Security settings deploy as a whole type. A file with more elements would overwrite those org values, which is why the check rejects any element other than the one setting.
