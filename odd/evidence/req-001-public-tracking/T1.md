## Decisions taken inside the decided scope
- Server split: the AC-001.1 call is literally `search('TRACKING_NUMBER', ['A, B', 'C'])` with 3 results expected, so the server also splits each entry on commas and line breaks (the same separators as the client, REQ-001) before trim / drop empties / upper-case / de-duplication. The raw-entry cap (>100) counts list entries before the split; the 10-value cap counts distinct values after it and stops normalizing at the 11th distinct value (bounded work).
- notFound lists each missing value once, in input order, with its first spelling as typed (trimmed), per S1 "keeping the first occurrence as typed".
- Messages: "Enter up to 10 values." for both count rejections (>10 distinct, >100 raw entries); "We could not complete the search. Please try again." for a mode outside the closed list and for any unexpected exception. Mode comparison is case-sensitive (Set.contains), so "tracking_number" is rejected.
- Matching of rows to typed values is case-insensitive in both modes (SOQL text comparison is case-insensitive; the found Name / Customer_Reference__c is upper-cased before comparison with the keys).
- Blank input (or a null list) returns an empty response without a query.

## Governor-limit notes
- search runs at most 1 SOQL query (0 when every value is rejected or invalid), returns at most 51 rows, and no DML.
- Normalization splits each entry; the work is bounded by the 100-entry cap and stops at the 11th distinct value, but a single entry can still be as long as the Aura payload allows (split cost proportional to its length). Any heap or CPU failure there becomes the generic message (X7).
- Test inserts call the access-code trigger (~8 ms CPU per row, foundation T2): the 251-row test spends about 2 s of CPU in setup.

## Security notes (sf-security-code-review)
- Entry point: `PublicTrackingController.search`, guest-reachable (profile classAccesses). Inputs: mode (closed list, case-sensitive), values (capped, length-checked, regex for tracking numbers). Sink: static SOQL with binds only (P8). Output: DTO with the seven BR-01 properties, no Id (P3, BR-03). Errors: two fixed messages, no exception text (X7). Misses: one notFound list, no reason (P4).
- `without sharing` only on the two-query helper, with SECURITY-JUSTIFICATION (pending owner approval, 2026-11-17) (P11). The DTO classes are `with sharing` (inner class declared separately).
- Out of scope, noted: C1 (no per-visitor rate limit; consecutive tracking numbers can be scraped for BR-01 data) stays for Hardening. The DTO class PublicTrackingResult has no guest class access; Aura checks access on the controller only, which T2's live call on the site should confirm.
