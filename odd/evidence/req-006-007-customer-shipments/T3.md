## Security and accessibility review

- experience-lwc-security-validate (review mode). All of lws-001 to lws-023b were walked across the four bundles. No match: no DOM sinks, no inner-html or lwc:dom, no eval or Function, no global assignment, no disallowed URL schemes. Set is used only through `.has()` (lws-016 clean). No mutation of server objects: values are copied into component-owned objects (lws-017 clean). Templates: every value is a text binding. The only bound hrefs are `BASE_PATH + "/shipment-detail?tracking=" + encodeURIComponent(value)` and fixed paths, so no scheme can be injected. Meta: targets are lightningCommunity__Page and __Default only, with no @api properties. Imperative Apex only, as the T2 controllers are not cacheable by design. Result: 0 findings.
- experience-accessibility-validate. Criteria evaluated: 1.3.1 (lists, groups and form labels: fieldset/legend, ul/li cards, dl), 1.3.5 (autocomplete on the customer's own pickup address, city and postal code; recipient fields off), 1.4.3 (night blue on white 15.2:1, white on electric blue 4.7:1, night blue on enamel gray 11.6:1), 2.4.3 (focus moves to the confirmation heading), 2.4.4, 3.3.1 / 3.3.2 (`*` marks with the hint "Fields marked * are required.", errors as text linked by aria-describedby, aria-invalid), 4.1.2, 4.1.3 (role=status quote, aria-live count, role=alert errors). 0 violations.
- Access code (A1, G5): it lives only in the component's `confirmation` field, is cleared by "Request another shipment" and by disconnectedCallback, and is never stored, logged or put in a URL. Jest spies on Storage.prototype.setItem and console, and source tests guard this; M-store proves both.
- Header links are navigation only. Access is enforced by the routes' pageAccess (proven live) and by the controllers' customer checks (T2).
