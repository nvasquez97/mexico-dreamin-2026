When Ana (with the seam set to Standard, so not guarded) inserted with Marta's account, the save failed with `INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITY, insufficient access rights on cross-reference id: 001Ek00002OvRTO`. 3. **Account__c read FLS: not possible. Replaced by an Id-only filter.** The handoff's remedy was read FLS on Account__c. The deploy refused it: `You cannot deploy to a required field: Shipment__c.Account__c`. Without Account Read, a user-mode query that names Account__c fails: `No such column 'Account__c' on entity 'Shipment__c'` (probe output below). Most conservative option, since Account Read is broader and G8 does not need it: the list and the detail are read in user mode with sharing, without Account__c. Then `MyShipmentsController.ownShipmentIds` keeps only the rows whose Account__c is the caller's account, using `SELECT Id ... WHERE Id IN :visible AND Account__c = :accountId WITH SYSTEM_MODE`. It returns only Ids and can only remove rows. A `// SECURITY-JUSTIFICATION` comment marks it, pending owner approval. Proof that this filter alone holds: mutation M7c (below) removes sharing and user mode but keeps the filter, and all 22 tests stay green.
4. **User.AccountId read in system mode.** A customer cannot read User.AccountId in user mode: `System.QueryException: No such column 'AccountId' on entity 'User'` (red `ctrl-1` below). `ShipmentRequestRules.customerAccountId()` is the only such read. It reads the caller's own User row and only that field, caches it per user and transaction, never sends it to the client, and has a SECURITY-JUSTIFICATION comment. Controllers and the trigger all use it. S1 called ShipmentRequestRules "pure functions"; this is the one exception, stated in the class header.
5. **Request shape:** `submitRequest(ShipmentRequestController.ShipmentRequest request)` takes a typed DTO with one property per AC-006.1 field. It is never a Shipment__c (X6), so it still receives individual fields.
6. **Guard on a user without an account:** a non-Standard user with no AccountId (for example the Automated Process user) is refused with `Shipments can be requested only by a customer account.`. This is conservative. No current automation inserts shipments as such a user (RunLocalTests: 478/478 green).
7. **Declared value with more than 2 decimals** is rejected, like the weight (G6 applied to the Currency(16,2) field). A missing declared value is rejected for customer inserts.
8. **Detail DTO** includes `lastLocation` (read FLS since T1, part of "last update") and the request date. It excludes the recipient's address, phone, email and the delivery instructions (G7).

## Security review (sf-security-code-review)

- Entry points:
  - `ShipmentRequestController.getQuote` and `.submitRequest`, `MyShipmentsController.listShipments` and `.getShipment` (all `@AuraEnabled`). Both classes are `with sharing`, API 67.
  - Class access is on RutaCargo_Customer only. The guest profile has none (guest-access-check). An explicit `UserInfo.getUserType() == 'Guest'` refusal plus the AccountId check refuse guests and internal users (tests run as the real site guest).
- P10 (user/system mode):
  - Every customer data read and the insert run in user mode.
  - Two justified system-mode reads (decisions 3 and 4). Neither returns data to the client beyond what user mode already returned.
- P8 (injection):
  - The list query string is built only from constants.
  - Status is validated against the active picklist values. The search term is trimmed, at most 50 characters, has `\`, `%` and `_` escaped, and is bound.
  - The tracking number is validated with `^RC\d{9}$` before a bound static query.
- X5/X6 (IDOR, mass assignment):
  - Detail is by tracking number, restricted to the caller's own account. Another customer's, an unknown or a malformed number gets the same "Shipment not found." message.
  - The request is a typed DTO. Account__c, Price__c, Status__c and Estimated_Delivery__c are never taken from the client, and the trigger enforces them for direct UI API creates too.
- BR-03: the DTOs carry no record or account Id, cost, margin, notes, hash or Proof_Id__c (JSON key-set assertions).
- Error messages are generic; no exception text reaches the client.
- G7 residual (unchanged, for Hardening): create FLS makes the 4 recipient fields readable through the API for the customer's own shipments.

## Governor-limit notes

- Trigger: no SOQL in loops. `customerAccountId` runs one query per user per transaction, and only for a non-Standard insert. The 251-row customer insert crosses the 200-row batch boundary and is green.

Worth a check at Close or Hardening.

### Security notes (sf-security-code-review, sf-security-access-review)

- P4/X11: the customer has no FLS on the four fields. The describe, user-mode SOQL and Shipment__History tests all prove it, and so do customer-access-check and the org FieldPermissions.
- P10: the only elevation is the trigger writing four staged fields. It is scoped and justified as above. No client can reach the stage: there is no @AuraEnabled path, and the public methods only stage or clear it.
- X6: a direct create, through the UI API or user mode, cannot carry the four fields, so the guard refuses it on each field. A system-mode create, which only Apex can do, must carry complete, valid recipient data.
- In user mode the error field names of the hidden fields are not returned to the customer, so no field metadata leaks.

- The guard adds no SOQL or DML: it runs field checks in memory per row.
- The 251-row customer insert (`customerInsert_isForcedToTheOwnAccountPriceStatusAndNoInternalField`) stays green.
