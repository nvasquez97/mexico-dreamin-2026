## Decisions and deviations recorded

1. **Deviation from a decided mechanism (no change to its contract): the issued codes list does not clear at every trigger batch.** The decision said the list is "cleared at the start of each before-insert batch, so for a single insert call the caller reads it right after insert". An Apex DML of 251 records runs the trigger in two chunks (200 + 51). With the literal mechanism, the caller of one insert gets back only the last 51 codes. The red is below under "Red of the as-decided mechanism": `Expected: 251, Actual: 51`. That breaks AC-F.4 and the decision's own contract ("same order as the inserted list"). Implemented instead: `DeliveryAccessCode.issueCodes` starts a new list unless the batch continues the same insert. A batch continues the same insert when the previous batch was a full 200-record chunk and `Limits.getDmlStatements()` has not changed. The public API (`lastIssuedCodes()`, `matches`, `generateCode`) and the "read it right after the insert" contract are unchanged. A dedicated test, `issuedCodes_holdOnlyTheLastInsert_whenASecondInsertFollowsAFullChunk`, proves that a second insert after a full 200 chunk starts a new list aligned with its own records.
   Known limits, for the main session and later tasks:
   - **Nested DML between chunks.** Automation added later could run DML between the two chunks of a large insert, for example in an after-insert of chunk 1. The second chunk would then start a new list, so the caller gets fewer codes than records. Callers can detect this by comparing sizes.
   - **Partial-success inserts.** `Database.insert(records, false)` retries re-run the trigger on the surviving records, which leaves the list misaligned. Callers that need the codes must use all-or-none inserts.
   - **Inserts on both sides of `Test.startTest()`.** `Test.startTest()` resets the limit counters. In a test, an insert of exactly 200 before `Test.startTest()` followed by another insert after it would look like one insert.
2. **Assumption for an undecided case (conservative): the caller cannot set the original estimate.** The decision says "fill Original_Estimated_Delivery__c when it is blank and Estimated_Delivery__c is set". While the original estimate is blank, the handler sets it to the shipment's Estimated_Delivery__c. If an update sets Original_Estimated_Delivery__c while there is no estimate, the value goes back to blank. Proved by `originalEstimate_staysBlank_whenAnUpdateSetsItWithoutAnEstimate`.
3. **Hash format.** `<base64 16-byte salt>$<base64 SHA-256(salt bytes + UTF-8 code bytes)>` is 24 + 1 + 44 = 69 characters, within Text(100). Salt: `Crypto.generateAesKey(128)`. The bytes are joined through hex (`convertToHex` / `convertFromHex`). `matches` checks the stored value against `^[A-Za-z0-9+/]{22}==\$[A-Za-z0-9+/]{43}=$` before decoding, so a malformed or caller-made value returns false instead of throwing. The comparison runs over the full expected length and starts from a length difference, with no early exit.
4. **Generator.** Each draw is `Crypto.getRandomInteger() & 31`, and 31 is rejected. That gives a uniform draw over the 31 characters, with no modulo bias and no Math.random. `generateCode_drawsEveryCharacterOfTheAlphabet` checks that 5000 draws reach exactly the 31 characters. The chance that a correct generator misses any character is about 31 × (30/31)^5000 ≈ 1e-70.
5. **Where the clear code can appear.** The clear code is never written to a field, a debug statement (there are none) or an exception message. Test assertion messages never print a clear code. They show the position, plus test-only hash values.
6. **SYSTEM_MODE in tests only.** At API 67 the running admin has no FLS on the new fields until T3, so the test DML and SOQL use `AccessLevel.SYSTEM_MODE` / `WITH SYSTEM_MODE`. This is justified in ShipmentTriggerHandlerTest by `// SECURITY-JUSTIFICATION: ... (pending owner approval, 2026-11-17)` (assumption A7). The production code has no system-mode operation and both classes are `with sharing`.
7. **GATE scope.** The handoff's GATE (`--source-dir force-app`) fails before any test runs: `An object 'rcHeader' of type LightningComponentBundle was named in package.xml, but was not found in zipped directory`. `force-app/main/default/lwc/rcHeader/` holds only an empty `.sf/` folder, and `digitalExperiences/site/RutaCargo1/` and `permissionsets/` are leftovers of the same kind. ### Design as implemented (within the decisions)

1. **Binding codes to Ids.** In before insert, each clear code is stashed in `pendingCodesByHash`, keyed by its stored hash. The random salt makes the hash unique per row. In after insert, `bindCodes` looks up each row's code by `Trigger.new[i].Delivery_Access_Code_Hash__c` and puts `Id -> code` into `issuedCodesById`. This is a decided "after insert maps Trigger.new[i].Id -> code" mapping, but keyed by the hash instead of the list position, so it holds when chunks are interleaved or nested DML runs between chunks. If a later automation changes the hash, that row gets no code; it never gets another row's code.
2. **Codes are kept only inside insertWithCodes.** The decision was to discard non-insertWithCodes codes at the end of the after insert. The fix is stricter: outside `insertWithCodes` (or the test hook), `issueCodes` does not stash the clear code at all. `insertWithCodes` uses a depth counter. Each call removes its own rows' codes as it returns them, and at depth 0 a `finally` block clears both maps, so a failed insert leaves nothing either. `lastIssuedCodes()` is removed. The maps are `@TestVisible private`.
3. **insertWithCodes runs in user mode only (assumption, conservative).** "The caller's mode" was read as user mode. A first draft added an overload `insertWithCodes(rows, AccessLevel)`. Code Analyzer flagged it as sev2 `ApexCRUDViolation` (DeliveryAccessCode.cls:72, 20261117-020740), and it would let a caller pass SYSTEM_MODE (policy P10). It was removed. The only API is `insertWithCodes(List<Shipment__c> rows)` with a literal `AccessLevel.USER_MODE`. The tests call it via `System.runAs` as a Minimum Access user. That user gets a test-only permission set (Account read, Shipment__c read/create, read/edit on the optional Shipment__c fields) and owns its own customer account.
4. **Test hook.** `@TestVisible private static Boolean captureForTest` lets the `Database.insert(rows, false)` test observe the Id binding. Production code never sets it.
5. **Stored value and matches.** The stored value is `v1$100$<24-char base64 salt>$<44-char base64 hash>`, 76 characters, which fits Text(100). `matches` first checks `^v1\$([1-9][0-9]{0,3})\$...$`, then rejects more than 1000 rounds, a bound against a CPU cost read from the field. It normalizes the input by removing `[\s-]` and upper-casing. The comparison runs in constant time, as before. The previous `<salt>$<hash>` format no longer matches. No such records exist outside tests (A6).
6. **Process notes.** In the first GATE try, the Metadata API returned `fetch failed`, a network error; a single retry passed. One mutation deploy went to the background and left source tracking stale, so `SourceConflictError: 2 conflicts detected` (ShipmentTriggerHandler) appeared. ### Governor-limit notes (CPU)

- Measured with anonymous Apex, no DML, wrapped in a savepoint and rollback, on 251 in-memory Shipment__c records: `CPUMEASURE issueCodes(251)=1997ms matches(251)=2048ms accepted=0 limit=10000`. That is about 8 ms of CPU per hash or check at 100 rounds, with debug logging on, so this is an upper bound.
- The 251-row insertWithCodes tests take about 1.5-2.8 s per test method, including DML and read-back. The slowest test is `partialInsert_everySuccessfulRowsCodeMatchesItsRecord` at 3.8 s, because the platform's partial-success retry runs the trigger twice.
- **Risk:** a single synchronous Apex transaction that inserts more than about 1,000 shipments, or checks more than about 1,000 codes, would approach the 10,000 ms CPU limit. Bulk API and Data Loader batches of 200 are separate transactions and are not affected. Callers that check codes should check one shipment per request. The hashing has no SOQL or DML, and heap use is negligible.

### Residual notes

- Under `captureForTest` only (tests), a partial-success first attempt can leave stale `pendingCodesByHash` entries until the transaction ends. Production stashes codes only inside `insertWithCodes`, which is all-or-none, so it never retries.
- A row whose hash another automation changes after `issueCodes` gets no entry in the returned map, rather than a wrong code.
