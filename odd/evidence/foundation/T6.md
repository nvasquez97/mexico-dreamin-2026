## Deviation from the handoff: the hash check

The handoff asked verify.sh to check Delivery_Access_Code_Hash__c "as admin via Tooling/data API". No user can read that field (D1, AC-F.8), the administrator included:

```
sf data query … "SELECT COUNT() FROM Shipment__c WHERE Delivery_Access_Code_Hash__c LIKE 'v1$100$%'"
No such column 'Delivery_Access_Code_Hash__c' on entity 'Shipment__c'.
```

Anonymous Apex runs with the caller's field permissions, and refuses system mode:

```
Compilation failed at Line 16 column 17 with the error: Cannot use SYSTEM_MODE access level in anonymous execution of Apex.
… ERROR at Row:1:Column:39 No such column 'Delivery_Access_Code_Hash__c' on entity 'Shipment__c'.
```

Granting read access or adding an Apex class would change metadata or Apex, which the handoff forbids. Instead:
- seed.apex rolls the whole load back unless `DeliveryAccessCode.insertWithCodes` returns exactly one code per shipment. insertWithCodes binds a code only to a row that stores the hash it generated (`bindCodes`, keyed by the stored `v1$100$…` value), so 120 codes prove the 120 hashes at creation, and the trigger reverts later changes to the hash (AC-F.13).
- verify.sh checks the local `.seed-output/access-codes.csv` when it is on the machine: header, 120 rows, exactly RC000001001–RC000001120, distinct 12-character codes from the alphabet. It never prints a code. When the file is missing it prints `skip:`, not `ok:`.

A direct check of the stored hashes needs a decision from the main session: an Apex check class, or read access on the field for the administrator.

## Incident: the first load's access codes were not captured

First real run of seed.sh (after two dry runs that threw before any DML: a compile check, then a state-check run reporting "0 account(s), 0 shipment(s); existing shipments 0"):

```
seed: test-tzfzdztrb3cf@example.com already has permission set RutaCargo_Support_Agent
seed: loaded 2 accounts, 2 contacts, ' + rows.size() + ' shipments ('
```

The load committed: 2 accounts, 2 contacts, 120 shipments. No code was extracted. Root cause, found with a probe that printed fake values (platform-apex-logs-debug): the platform writes `|` inside a USER_DEBUG message as `&#124;`, and the log also echoes the Apex source:

```
Execute Anonymous:     System.debug(LoggingLevel.INFO, 'SEEDCODE|' + 'RC00000000' + r + '|' + 'TESTTESTTEST');
05:27:48.27 (28352376)|USER_DEBUG|[2]|INFO|SEEDCODE&#124;RC000000000&#124;TESTTESTTEST
```

So the status grep matched the echoed source line, and the code grep matched nothing. Under `set -e` the script stopped inside the redirected block, and the EXIT trap's message went into the temp file. That file held only a header and the trap line, and was removed. No code was written anywhere and none was printed. No ApexLog was persisted (no trace flag; "deleted 0 debug log(s)"). Only the hashes are stored (D1), so **the 120 clear codes of the shipments seeded in cargo-opus-t1 are lost**. Nothing was deleted or reloaded. Recovery is for the main session to decide: a new scratch org seeded from zero, a destructive cleanup (the Auto Number would not return to RC000001001), or a code-reissue path. README lists this under the owner's manual steps.

Fix in seed.sh, in the task commit: the parsing is in `debug_lines`, `status_from_output` and `codes_from_output`. They keep only USER_DEBUG lines and decode `&#124;`. The code count is checked before anything is written, and the trap writes to stderr. Proof on a real platform response from an anonymous block that printed 120 **fake** codes (`FAKE00000000`…) in the seed's exact format, parsed by the functions extracted from seed.sh:

```
status: SEED|loaded|2 accounts, 2 contacts, 120 shipments (probe)|probe
codes: 120 first: RC000001001,FAKE00000000 last: RC000001120,FAKE00000119
3-line probe: 3 codes, status SEED|loaded|probe
```

Lesson for later seeds: probe the output format with fake values before the first committing run.

## Governor limits and risks

- One load transaction: 5 SOQL, 4 DML statements (accounts, contacts, the shipment insert, the status update), 244 DML rows. The 120 iterated hashes take about 1 s of CPU (about 8 ms each, T2 memory note), far below 10 s. More than about 1,000 rows in one call would approach the CPU limit.
- Clear codes exist only in the CLI response held in a shell variable, then in `.seed-output/access-codes.csv` (umask 077, chmod 600, git-ignored: `git check-ignore -v .seed-output/access-codes.csv` → `.gitignore:54:.seed-output/`). The anonymous log level is DEBUGONLY (apex-node `debugLevel`), so no VARIABLE_ASSIGNMENT lines are logged. The run's ApexLog rows are deleted when there are any.
- The seed must be loaded in a new org. Any Shipment__c ever created, deleted ones included, makes it refuse to load.
