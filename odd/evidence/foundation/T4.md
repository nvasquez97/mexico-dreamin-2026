## Findings and notes for the main session

- enableSecureGuestAccess: the deploy of Sharing.settings-meta.xml succeeds (Settings Sharing "Changed", twice, once alone) but a retrieve still reads `<enableSecureGuestAccess>false</enableSecureGuestAccess>`. The platform accepts and ignores the value; it does not refuse it. The file is versioned as the handoff decided; the value it states is not what the org reports.
- Fresh-scratch portability: this GATE runs against the same org, so it proves the package redeploys, not that it creates the site from zero. Risks for a fresh scratch: (a) the guest profile `RutaCargo Profile` is created by the Network deploy; if the Profile is processed first it may fail or be created as a separate profile; (b) the `MicrobatchSelfReg` page is created by the platform with the site (CreatedDate equal to the site creation), so the profile's pageAccesses entry needs it to exist by then; (c) `noreply@example.com` as sender address triggers a verification email and stays pending; (d) the sfdc_cms__styles `ref` Ids are org-specific (0sN...), they are regenerated on each deploy and the deploy with a stale ref succeeded here.
- After a deploy, a retrieve differs only by server normalization: empty `"dxpStyle" : { }` keys in views and theme layouts, new style refs, the pending sender address and the user-specific CustomSite fields removed on purpose. The committed files are the deployed versions.
- Network keeps `<tabs><standardTab>Chatter</standardTab>` and enableDirectMessages true as created by the template; guest Chatter is off.
- Bundle redeploys need `sf community publish` to go live (the GATE deploy kept the published state here, check green after it).
- Governor limits: none relevant; the setup Apex runs 2 SOQL and at most 1 DML.
