## Design notes (inside the decided design)

- Binding of the reissued code: the decision says "after update binds code to Id like insertWithCodes". ShipmentTrigger has no after-update event and `force-app/main/default/triggers/ShipmentTrigger.trigger` is not in the Touch list, so the binding happens in before update, where the record Id already exists (unlike before insert): `DeliveryAccessCode.replaceReissuedCodes` (called by `ShipmentTriggerHandler.beforeUpdate` after the protected-field revert) generates the code, overwrites the hash and stores code by Id; `reissueCodes` returns them after its all-or-none `Database.update(rows, true, AccessLevel.USER_MODE)` succeeds and clears both static structures in `finally`. If a later step re-fires before update in the same DML (e.g. an after-save flow), the code is regenerated and the map entry is overwritten with it, so the returned code always matches the last stored hash. Result is the same contract (map for exactly the given Ids, codes verify); reviewers may want the trigger event added in a later task if they prefer the literal design.
- verify: `WITH SYSTEM_MODE` only on the one-Id hash query, with the SECURITY-JUSTIFICATION comment `(pending owner approval, 2026-11-17)`; class stays `with sharing`, so record sharing still applies to that query. No @AuraEnabled.
- Test fixture: the support agent in DeliveryAccessCodeTest is a Standard Platform User with the RutaCargo_Support_Agent permission set and manual Edit shares to the user itself (not the RutaCargo_Support_Agents group). A first version added the agent to the group; under parallel test execution that made SupportAgentAccessTest's GroupMember insert fail with `UNABLE_TO_LOCK_ROW` (8 tests, see the first M2 run below). Sharing to the user removes the shared lock.

## Governor-limit notes

- reissueCodes: one DML for any number of Ids; CPU about 8 ms per shipment for the 100-round hash (120 seeded shipments in one call; a 251-record call runs in the tests). Very large sets (more than about 1000 in one transaction) would approach the 10 s CPU limit; callers should chunk.
- verify: one SOQL per call by design (single record). verify.sh therefore runs the 120 checks in batches of 50 per anonymous execution (51 queries each, under 100).
