## Design notes
- Response wrapper: `RecipientDeliveryController.DeliveryResponse {outcome, message, details}`; outcomes SUCCESS, NOT_MATCHED, LOCKED, REJECTED. `details` only after a successful verification (also on a REJECTED reschedule, with the current values).
- Closed list of messages: "The details do not match this shipment"; "Too many attempts. Please try again in 15 minutes."; window "The new delivery date is outside the allowed rescheduling window."; status "This delivery cannot be rescheduled in its current status."; limit "This delivery has already been rescheduled the maximum number of times."; no estimate "This delivery has no estimated date to reschedule from yet."; instructions "Delivery instructions must be 1000 characters or fewer."; unexpected error (AuraHandledException) "We could not complete your request. Please try again later."
- deliveryAddress is composed as `<Recipient_Address__c>, <Destination_Postal_Code__c> <Destination_City__c>` (blank parts skipped). rescheduleFrom/rescheduleTo are filled only when canReschedule (status allowed, count < 2, original estimate present, today+1 <= original+7).
- Equal hash work: DeliveryAccessCode.DECOY_STORED_VALUE is private and DeliveryAccessCode.cls is out of scope, so RecipientAccess carries its own well-formed v1 decoy (fixed public salt, 100 rounds). A malformed or blank code is replaced by a 12-character filler outside the code alphabet so `matches` always computes exactly one stored value (it returns before hashing on a blank code). Proven: every failure and a success cost exactly 1 (`shouldDoOneHashForEveryFailureAndForSuccess_WhenAnyValueIsWrong`).
- Counting: `upsert` on Shipment_Key__c (creates or touches and locks the row), re-read `FOR UPDATE`, increment; a concurrent first insert that fails with DUPLICATE_VALUE is retried once. The shipment is read with no lock for verification; `FOR UPDATE` on Shipment__c only in lockForReschedule, and the rules are re-checked on the locked row before saveReschedule.
- T2 seam: `RecipientAccess.verifyBeforeCallout` (a failure is counted; a success makes no DML and takes no lock - proven with Limits.getDmlStatements) and `RecipientAccess.resetAttempts` (after the callout, locks only the guard row). Verification is built only by RecipientAccess; its shipment copy has no Id, no Name and no hash.
- Test seams: `RecipientDeliveryController.todayOverride` (today in America/Mexico_City) and `simulateUnexpectedFailure` (raises inside the guarded block to prove the generic AuraHandledException).
- Test data: shipments are inserted only inside tests (A6) via TestDataFactory.insertShipmentsWithCodes, which captures the clear code from DeliveryAccessCode while the insert runs and clears it afterwards; codes never reach a field, a log or this file.
