## The stop (first run) and E11
The first run used the External Credential design: `EntregaYa` (Custom protocol, an AuthHeader built from the named principal `EntregaYaPrincipal`) and the permission set `RutaCargo_Guest_Proof_Download`, which held only the principal access. Both deployed, and the assignment to the site guest user succeeded with 0 object permissions. A live anonymous call of downloadProof on the site, for seeded Delivered shipment RC000001001 (verified), was traced. The guest's debug log showed:

```

EXCEPTION_THROWN|[104]|System.CalloutException: You don't have read permissions on the User External Credential object.
```

This hit the handoff's STOP condition, so the run returned without committing. The main session recorded **E11**: use a password-authenticated Named Credential, with no permission set and no External Credential for the guest. The fallback (exactly one guest Read on UserExternalCredential) applies only if the platform refuses the password credential.

What the platform did with the password credential:
- Creating `EntregaYa_API` from force-app's file (which has no password) was refused: `A password is required for the specified authentication protocol.`
- Updating an existing credential with the same password-less file succeeded. I created it from a scratchpad copy with the non-secret placeholder password `not-set-enter-the-key-in-setup`, then deployed the repository file over it: `Succeeded`.
- So the platform does not refuse the credential. It refuses only a password-less creation. `scripts/setup/guest-proof-access.sh` creates the credential once, before the force-app deploy (DEPLOY-ORDER step 1b), with that placeholder, from a temporary folder. It never touches an existing credential, so the owner's key is kept. The fallback was not needed.
- Not proven: whether a later force-app deploy (file without a password) keeps a password the owner entered. There is no endpoint that echoes the header. The README asks the owner to check the download again after a later deploy.

## Governor-limit notes
- The synchronous heap holds the response body, its parsed copy and the decoded PDF. The 2,500,000-character cap is checked before parsing, and the at-cap test passes. `fetch` does not keep the body after parsing.
- downloadProof makes one callout per call. RecipientAccess.verifyBeforeCallout runs 2 SOQL queries before it (the shipment by Name and its guard row), and there is no DML before it. The callout timeout is 10 seconds of the 120-second limit.
- A verified download resets a non-zero counter after the callout: 1 SOQL query with FOR UPDATE and 1 DML statement on the guard row only.
