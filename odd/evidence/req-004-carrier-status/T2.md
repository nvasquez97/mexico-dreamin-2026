## Notes, risks and decisions inside the handoff
- Lock mapping (B7). The update uses `Database.update(change, false, AccessLevel.USER_MODE)` and maps the SaveResult StatusCode: UNABLE_TO_LOCK_ROW gives RETRYABLE/TEMPORARILY_UNAVAILABLE, any other code gives INTERNAL/INTERNAL_ERROR. The FOR UPDATE wait timeout is a QueryException with no StatusCode, so it is matched on its message ("UNABLE_TO_LOCK_ROW" or a message starting with "Record Currently Unavailable"). Every other exception is caught and gives INTERNAL; nothing is rethrown. This is a deviation from the handoff wording ("DmlException whose StatusCode is UNABLE_TO_LOCK_ROW"). `getNumDml()`/`getDmlType()` on a DmlException without DML rows throws an uncatchable System.UnexpectedException (seen in run 707Ek00003UyYhP), which would break "never rethrow". The SaveResult status code gives the same StatusCode check without that risk. The real FOR UPDATE timeout message cannot be produced in an Apex test.
- Seams. `@TestVisible nowOverride` fixes the clock, because the AC timestamps (2026-11-20/21) are after today's date (2026-11-17) and would otherwise fail B5. `@TestVisible simulatedFailure` is an enum (LOCK_ON_UPDATE, LOCK_ON_QUERY, UNEXPECTED_DML, UNEXPECTED_OTHER) for T3 to reuse. The anonymous-Apex probe showed that constructed exceptions can be thrown and caught, which pointed to getNumDml as the cause.
- Fractions of a second are accepted and dropped: two updates within the same second compare equal, and the second one is IGNORED.
- isApplying() is true only around the service's own update and is reset in `finally`. A test proves it is reset after a failed call.
- Governor limits: the service uses 1 SOQL and 1 DML per call. The trigger guard makes 1 FeatureManagement.checkPermission call per trigger batch (no SOQL/DML) and is bulk-proven at 251 records for both the agent and the integration user.
- Out of scope: a proofId longer than 100 characters (Proof_Id__c length) fails the save and returns INTERNAL_ERROR (500), not a 400. The closed code list has no code for it; T3 or the main session may want a length check.
- SECURITY-JUSTIFICATION (SYSTEM_MODE) appears only in test code (TestDataFactory helpers, EntregaYaStatusServiceTest fixture), approver "(pending owner approval, 2026-11-17)" (A7). Production code has no SYSTEM_MODE and is `with sharing`.
- No Shipment__c was inserted outside Apex tests (A6). The anonymous Apex probe did no DML.
