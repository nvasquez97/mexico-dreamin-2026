## What the platform required (findings)

- The global OAuth settings need a callback URL even for client credentials
  (`[Enter a callback URL in a valid URL format]` on the dry run). A placeholder
  `https://localhost/entregaya/no-callback` is used: PKCE and the secret are
  required, users must be pre-authorized and the only one is API-only.
- The platform creates the OAuth policy `EntregaYa_Status_oauth_defaultPolicy`
  with the app (client credentials off, AllSelfAuthorized, Enforce). The
  template carries that name, so the setup deploy updates it.
- `ExtlClntAppOauthPlcyCnfg.ClientCredentialsFlowUser` holds the user Id, not
  the username (the check compares Ids).
- Pre-authorizing the permission set adds a SetupEntityAccess row
  `ExternalClientApplication:<app Id>` to RutaCargo_EntregaYa_Integration;
  section 2b of the access check now expects exactly the class, the custom
  permission and that app.
- A profile deploy does not revoke a class access that is only absent from the
  file: reverting the AC-004.8 mutation needed an explicit
  `<enabled>false</enabled>` deploy, then the file was restored to HEAD.
- The LWR site runtime answers any POST under
  `/rutacargo/services/apexrest/*` with 501 and the site's HTML error page, the
  same for a resource that does not exist. **Deviation from the AC's literal
  list (401/403/404):** attack-check accepts 501 on that path only when a
  control POST to a non-existent resource under the same prefix also answers
  501 and the body is not the resource's envelope (not routed to Apex). Never
  200. The main session decides whether the AC text should list 501.
