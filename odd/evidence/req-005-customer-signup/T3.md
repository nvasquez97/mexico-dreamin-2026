## Decisions recorded

- Sign-up success flow (handoff: "choose the simplest correct flow"): `signUp` returns `{success: true, code: CREATED, message: "Your account is ready. Log in with your email and password."}` and no session, so rcSignUp replaces the form with that message (role=status) and a "Log in" link to `<basePath>/login`. It does not call `login` with the password it just sent (the password is read from the input at submit and kept nowhere).
- Form controls: native `<form>`, `<input>`, `<label for>`, `<fieldset><legend>` for the customer type radios, and per-field error `<p>` linked with `aria-describedby` + `aria-invalid`, instead of `lightning-input` / `lightning-radio-group`: the duplicate-email message must hold a link (a `setCustomValidity` message is plain text) and the per-field server message must be the same text node the visitor and Jest read. Native `<button type="submit">` gives Enter-to-submit. (Base-components skill guidance prefers LBC; recorded as a deliberate deviation.)
- Client rules mirror the server exactly (same messages): customer type in {Individual, Business}; name ≤ 255, first ≤ 40, last ≤ 80 (trimmed, not blank); email trimmed + lower-cased ≤ 61 and the server's regex; phone `[0-9+() .-]`, ≤ 40, ≥ 7 digits; password 10..128 with a letter and a digit; confirmation equal (client-only message "Enter the password again." for a blank confirmation). A server `field` puts the message under that field; `EMAIL_REGISTERED` adds the "Log in" link; no field → form-level alert; a rejected call → generic message, never the error detail.
- rcLogin: startURL from `window.location.search` only if exactly "/", "/my-shipments" or "/request-shipment", else "/"; success → `NavigationMixin.Navigate({type: "standard__webPage", attributes: {url}})` only for an `https://` URL or a site-relative path (not `//`), never logged or stored; any failure → the one message "Your email or password is incorrect." and the password input cleared.
- rcForgotPassword: after `forgotPassword` resolves (any value) → `comm__namedPage` `Check_Password`; a rejection → generic message, stays.
- rcHeader: second landmark `<nav aria-label="Account">` (the Main nav keeps its one Track link): guests "Log in" (`/login`) and "Sign up" (`/SelfRegister`), logged-in users "Log out" (`<basePath>` + `LOGOUT_PATH` = `/secur/logout.jsp`, from `@salesforce/user/isGuest`). Confirmed live: `/rutacargo/secur/logout.jsp` → 301 → `/rutacargovforcesite/secur/logout.jsp` → 200, whose script sends to `https://…/rutacargo/login`.
- Existing rcHeader test "builds the home links from the site base path" selected every `<a>`; its selector now reads the brand link and the Main nav only (`a.rc-header__brand, nav[aria-label="Main"] a`), same expectation. All other REQ-001 header tests (logo widths, A14 alt texts, font) unchanged and green.
- Views: the three `community_login:*` nodes are replaced by `c:rcSignUp`, `c:rcLogin`, `c:rcForgotPassword`; siteLogo, employeeLoginLink (login view) and seoAssistant are kept. The content.json files keep the platform's own JSON layout (` : `), as at HEAD; prettier is not applied to them.
- Test password values live in constants (`VALID_PASS`, …) because guest-access-check.sh's repository secret scan refuses `password: "<8+ chars>"` literals (its first run on T3 failed on 16 test lines; same pattern T2 used in Apex). They are the AC-005.4 rule values, not credentials.

## Owner report: sign-up error "accountId parameter value is not valid" (read-only investigation)

Relayed by the main session after the T3 commit. Investigated read-only; no live sign-up was submitted; nothing in T2/T1 scope was changed.

- Owner and role (hypothesis 1, ruled out): both sites RutaCargo and RutaCargo1 have `GuestUserId 005Ek00000vquTeIAI` (RutaCargo Site Guest User, UserType Guest, no role, profile RutaCargo Profile) and `GuestRecordDefaultOwnerId 005Ek00000voo5hIAA` (User User, System Administrator, active, role `RutaCargo_Customer_Owner` 00EEk00000I3u9lMAB, PortalType None). The seeded customer accounts are owned by that user with that role.
- Business account (hypothesis 2, ruled out): `SELECT IsPersonAccount FROM Account` → `INVALID_FIELD: No such column 'IsPersonAccount'`: Person Accounts are not enabled, every Account is a business account.
- Guest-created records: none remain (Accounts: Abarrotes Acme, Globex Farma, Sample Account for Entitlements only; Contacts: the two seeded ones; Customer Community 2/5) — CustomerRegistration rolls back the Account and Contact on any createExternalUser failure, so the owner of the guest-inserted Account cannot be read after the fact. No ApexLog and no TraceFlag exist.
- Visibility (hypothesis 3, most likely, not yet proven by a log): the guest has no Read or Create on Account or Contact (no ObjectPermissions rows for its profile or permission sets), and Account and Contact are Private internally and externally. CustomerRegistration inserts the Account in system mode; with secure guest record access the Account is owned by the default owner, so the guest itself cannot see it. `Site.createExternalUser(user, accountId, password)` validates the accountId in the running guest context. Consistent live evidence: the standard `applauncher.SelfRegisterController` called by the guest with an existing customer accountId answered `Insufficient Privileges: You do not have the level of access necessary to perform the operation you requested.` (F9 above).
- Secondary candidate: `newUser.ContactId` is set to the pre-inserted Contact and the accountId is passed as well; the platform may refuse the pair. Only a debug log of one attempt separates the two.
- Next step proposed (needs the main session's decision, it consumes a license only if it succeeds): one traced attempt — a TraceFlag on the guest user 005Ek00000vquTeIAI, then one rcSignUp submit with a fake example.com email — to read the exception and the line. The fix is in CustomerRegistration / the access design (T2 or a new task), outside the T3 Touch list.
- What the visitor sees: CustomerRegistration catches every createExternalUser exception and returns `FAILED`; CustomerSignUpController maps it to `MESSAGE_FAILED` ("We could not create your account. Please try again later."); rcSignUp renders the server's `message` as text, and a rejected call as that same generic text (Jest: `a rejected call shows the generic message, never the error detail`). So the raw platform text never comes from this path. rcSignUp does display any server message string up to 300 characters; an allow-list of the server's known messages (as rcTracking does) would make it independent of the server contract — a defense-in-depth change for a fix round, not made here.
