## Design inside the decided contract

- **Seams.** `CustomerRegistration.gateway` (`SiteGateway`: validatePassword, createExternalUser) and `CustomerLoginController.gateway` (`SiteAuthGateway`: login, forgotPassword), both `@TestVisible private static`. The first name `site` did not compile: Apex is case-insensitive, so a static field `site` shadows the `Site` class inside the inner gateway (`Illegal assignment from String to System.PageReference`); renamed to `gateway` (the stub red phase used the name `site`).
- **Result contract for T3.** `signUp` returns `SignUpResult {success, code, field, message}`; code is `CREATED`, `INVALID` (field = the form field: customerType, accountName, firstName, lastName, email, phone, password, confirmPassword), `EMAIL_REGISTERED` (field email, "This email is already registered. Log in instead.") or `FAILED` (generic). The first invalid field in form order is returned. `login` returns `LoginResult {success, redirectUrl, message}`; `forgotPassword` returns `true` always. Messages are constants and never echo input.
- **Field limits.** Account.Name 255, Contact.FirstName 40, LastName 80, Phone 40 (characters `0-9 + ( ) . -` and space, at least 7 digits), email ≤ 61 after trim + lower case and a format pattern, password 10..128 with a letter and a digit. The confirmation is compared with `String.equals`: Apex `==` ignores case (test `signUp_confirmationDiffersInCase_isRejected` uses the same value in lower case).
- **Confirmation message.** A differing confirmation returns field `confirmPassword` with "The password and its confirmation do not match." (AC-005.4 says "the password message"; I read it as the password-related message of that field, not the length/complexity text). Main session may want to confirm the wording for T3.
- **Uniqueness.** Contact.Email of accounts with Customer_Type__c set (the RutaCargo customer accounts) and User.Email of users of the profile "RutaCargo Customer" with no IsActive filter. SOQL `=` on Email is case-insensitive; the email is normalized anyway.
- **Username lookup** (`activeCustomerUsername`): ACTIVE users of the profile only, exactly one row (LIMIT 2), else null; emails over 80 characters are not queried.
- **CustomerPermissionAssigner is `without sharing` (justified).** First built `with sharing`: the job runs as the user who enqueued it (the guest), who cannot see the new user under sharing, so its profile check found nothing and nothing was assigned (red below, run 707Ek00003V2XHt). It assigns only the constant RutaCargo_Customer, only to a user of the profile "RutaCargo Customer", only once (two tests: an internal user gets nothing; a second run keeps one assignment). Its comment carries the SECURITY-JUSTIFICATION (pending owner approval, 2026-11-17). This is a second without-sharing class beyond the one the handoff named; it is not a guest entry point (no class access, checked by both scripts).
- **System mode.** Both without-sharing classes use `WITH SYSTEM_MODE` / `AccessLevel.SYSTEM_MODE` explicitly: at API 67 user mode is the default and the guest has no object or field permission.
- **Tests and seats (F7).** No portal user is inserted. The seam "creates" the seeded Marta Ruiz (her RutaCargo_Customer assignment is removed inside the test so the job's assignment is observable); login and reset use the seeded Ana López; the inactive-user case deactivates Marta inside the test. The internal-user case uses `UserInfo.getUserEmail()` of the running admin (no email literal). Test password values are held in constants not named `password` so guest-access-check 5d's password-literal scan stays clean (it passed).
