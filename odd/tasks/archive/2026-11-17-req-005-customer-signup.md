## Findings

- D5 (.mem/memory.md): business Account + Contact for both customer types (no Person Accounts); Customer Community license; Shipment__c external OWD Private; sharing set on Account__c (the sharing set belongs to REQ-007/REQ-006, which give customers their shipments). A4 (foundation): the site users of the two test customers are created by REQ-005, which owns the customer profile and the account-owner role.
- Licenses: Customer Community 0/5 used (two for Ana López and Marta Ruiz; three left for sign-ups); Salesforce 2/2; Salesforce Platform 0/3 (.mem/memory.md). Standard profiles with Customer Community licenses exist ("Customer Community User").
- The network "RutaCargo": selfRegistration false, members only the admin profile, login/forgot-password/self-register pages overridden by the LWR site (Designer); sendWelcomeEmail true (`force-app/main/default/networks/RutaCargo.network-meta.xml:38-55`). The LWR views use the standard `community_login:selfRegister`, `community_login:loginForm` and `community_login:forgotPassword` components (`force-app/main/default/digitalExperiences/site/RutaCargo1/sfdc_cms__view/{register,login,forgotPassword}/content.json`).
- The Visualforce self-registration pages are refused by guest-access-check.sh section 7 and are not in the guest page allow-list (foundation AC-F.9).
- Seed: Abarrotes Acme / Ana López (ana.lopez@example.com) and Globex Farma / Marta Ruiz (marta.ruiz@example.com), Business accounts (`scripts/seed/seed.apex:113-116`).

- With secure guest record access (enforced), records a guest creates are owned by the site's default record owner (CustomSite field `siteGuestRecordDefaultOwner`, an org-specific username; today the org's admin, the site creator, who has no role), and an Account that owns external users must be owned by a user with a role.
- REQ-001 and REQ-002+003 add guest-callable controllers and an exact class allow-list in guest-access-check.sh; rcHeader holds the main navigation (`force-app/main/default/lwc/rcHeader/rcHeader.html`).

## Problems
- P1: Customers cannot create an account or log in to request shipments (evidence: REQ-005 story).
- P2: A guest-callable sign-up creates records and users: mass-assignment (an SObject from the client), injected owner or profile, or bypass of the one-account-per-email rule would let anyone create privileged or duplicate users (evidence: AC-005.2, AC-005.3, X6, X11).
- P3: Login and password reset by email could reveal which emails are registered or allow unlimited password guessing; an unchecked startUrl is an open redirect (evidence: AC-005.5, AC-005.6, X4, X16, X10).
- P4: A customer profile or permission set broader than needed exposes internal fields (credit limit, credit risk) or other customers' records (evidence: BR-03, BR-07, P4, X11).
- P5: Org-specific values (the default record owner's username, global usernames) in versioned metadata break the next org's from-zero deploy (evidence: foundation A11, REQ-004 S4 precedent).
- P6: AC-005.3 itself discloses whether an email is registered; unlimited sign-up attempts would let anyone enumerate customer emails or exhaust the Customer Community licenses (evidence: AC-005.3, X16, licenses 5).

## Solutions
- S1 → P4, P5: access configuration. A custom profile "RutaCargo Customer" (Customer Community license; minimal: no object permissions beyond what the license requires) and a permission set `RutaCargo_Customer`, the single actor-specific grant, created now with no object permissions (REQ-005 needs none: login needs no data; REQ-006/007 add Shipment__c, Account and Contact access together with the sharing set that limits them to the customer's own records) and assigned to every customer. A ProfilePasswordPolicy for the profile (profilePasswordPolicies/; validated first with a check-only deploy): minimum length 10, complexity alpha and numeric, lockout after 5 invalid attempts for 15 minutes, passwordExpiration 90 days, passwordHistory 3, passwordQuestion none; the check retrieves it (it is not readable by SOQL). A role `RutaCargo_Customer_Owner` for the internal owner of customer accounts; `scripts/setup/customer-owner.sh` reads the site's current guest default record owner (`Site.GuestRecordDefaultOwnerId`; CustomSite field `siteGuestRecordDefaultOwner`, today the org's admin, the site creator) and assigns it that role, failing if no owner is set — no site template, sites/RutaCargo.site-meta.xml is not touched. The Network: force-app's RutaCargo.network-meta.xml holds the final state (the customer profile as a member, selfRegistration true, selfRegProfile "RutaCargo Customer"), so every gate deploy keeps it; because the platform needs two phases (the profile a member first, then self-registration on) and a new org deploys the network before the profile exists, scripts/setup/DEPLOY-ORDER.md gets the from-zero order (profile → network with the member only, via a bootstrap copy in scripts/setup/templates/ → force-app network) and customer-owner.sh applies the two phases idempotently. Discarded: Person Accounts (D5); granting through the profile only (P4: permission sets per actor); the standard "Customer Community User" profile (shared, not least privilege); `username = email` (global collisions); Account/Contact grants now (a permission set cannot limit them to own records without the sharing set; REQ-006/007).
- S2 → P2, P6: a guest-callable `CustomerSignUpController.signUp(customerType, accountName, firstName, lastName, email, phone, password, confirmPassword)` (`with sharing`, individual fields, non-cacheable) that validates everything server-side (closed list for customerType, lengths of the target fields, email format and at most 61 characters — the username adds a 19-character suffix and Username allows 80 —, phone characters, password policy ≥ 10 with a letter and a digit and `Site.validatePassword`), normalizes the email (trim, lower case) and checks uniqueness against Contact.Email of RutaCargo customer accounts and User.Email of active AND inactive users of the profile "RutaCargo Customer" through a small `without sharing` helper `CustomerRegistration` (`// SECURITY-JUSTIFICATION`, pending owner approval); a duplicate returns "This email is already registered. Log in instead." with no records created; otherwise the helper inserts the Account (Name, Customer_Type__c; owner set by the platform's default owner rule) and the Contact (first and last name, email, phone), then calls `Site.createExternalUser(user, accountId, password)` with a server-built User (username = normalized email + "." + the 18-character org Id in lower case; CommunityNickname = email local part (≤ 30) + "-" + 6 random characters (unique in the org); Alias = first 4 letters of the local part + 4 random characters (8); LanguageLocaleKey/LocaleSidKey en_US/es_MX; TimeZoneSidKey America/Mexico_City; Email the normalized email; ProfileId resolved on the server from the constant profile name "RutaCargo Customer", never from the client), all in one transaction with a savepoint: any failure rolls back the Account and Contact and returns a generic message. After the user exists, a Queueable `CustomerPermissionAssigner` assigns RutaCargo_Customer (a PermissionSetAssignment in the same transaction would be a mixed DML after the Account and Contact inserts). Discarded: the standard selfRegister component (cannot collect customer type and legal name with these rules); a whole User or Account from the client (X6); a CAPTCHA (no third-party script host is allowed on the site; recorded for Hardening).
- S3 → P3: a guest-callable `CustomerLoginController` (`with sharing`): `login(email, password, startUrl)` resolves the active user OF THE PROFILE "RutaCargo Customer" by normalized email through `CustomerRegistration` (system mode, returns only the username internally; an internal user's email is never resolved, so the site can neither log in nor send a reset link to an internal user) and calls `Site.login(username, password, startUrl)`; an unknown email or a wrong password returns the same "Your email or password is incorrect." (the platform lockout policy of S1 limits guessing); startUrl is accepted only as a site-relative path from a closed list ("/", "/my-shipments", "/request-shipment") else "/"; `forgotPassword(email)` calls `Site.forgotPassword(username)` only when the user exists and always returns the same result, after which the LWC shows the check-email page. Logout: rcHeader shows "Log in" and "Sign up" to guests and "Log out" (the site's `/secur/logout.jsp` under the LWR site's base path, /rutacargo; the worker confirms the path live) to logged-in users; a live check proves the logout URL answers with a redirect back to the site, never 404. Discarded: the standard loginForm (expects the username, which is not the email); a custom password reset token (the platform link is enough and safer).
- S4 → P1: LWCs `rcSignUp`, `rcLogin`, `rcForgotPassword` on the register, login and forgot-password views (replacing the standard components there; the check-email view stays), with client-side validation mirroring the server (password rule, confirmation, required fields, customer type radio), generic server messages shown as text, mobile first, brand palette; Jest with Sa11y.
- S5 → P1: the two seeded customers get active site users (Ana López, Marta Ruiz) through `scripts/setup/seed-customer-users.sh` (idempotent; same username rule and profile; permission set RutaCargo_Customer assigned; no password printed: the platform sends the welcome/reset email, or the owner resets in Setup).
