## Problems
- P1: A leaked credential stays usable until rotated, and nothing stops the next secret from being committed (evidence: SEC-001).
- P2: A guest can learn every recipient's postal code and deny any recipient access to their delivery (evidence: SEC-002, SEC-011).
- P3: A per-pair guard lets an anonymous guest create a guard row per new typed postal code, without limit, until storage or guard DML fails (evidence: plan review of S1).
- P4: Either administrator's stolen password gives full control of the org (evidence: SEC-003).
- P5: Two analyzer High violations remain in the code base; one test depends on org data (evidence: CA-001, CA-002).

## Solutions
- S1 → P2: key the failure guard on the pair (shipment, typed postal code): `Shipment_Key__c` = shipment Id + ":" + hex SHA-256 of exactly `normalizedPostalCode(typed)` (a blank value becomes a fixed token; widen the field; update schema-check.sh and the guard descriptions). Count every failure for an existing shipment under the pair's key, whatever the postal code; check the lock of that same pair. Before comparing, read an existing pair row with `FOR UPDATE`; make no DML on success (the downloadProof callout follows). Every postal code then answers the same way (5 NOT_MATCHED, then LOCKED), an attacker who does not know the recipient's postal code cannot lock the recipient's pair, and the 5-attempt limit per pair stays. Unknown tracking numbers never create a guard (tracking numbers are public; intended). Discarded: counting by tracking number only (removes the oracle but lets anyone lock any recipient knowing only the public number); two buckets right/wrong per shipment (the wrong bucket locks first and reveals the right postal code); removing the lockout (X16 requires an attempt limit); CAPTCHA (no third-party script host allowed on the site); a site rate limit (infrastructure, owner).
- S2 → P3: bound the guard rows: a typed postal code longer than 10 characters after normalization (longer than Destination_Postal_Code__c, Text 10, so no stored code can equal it) is counted under one fixed per-shipment "malformed" key, with the same response and hash work; every value of 10 characters or fewer, punctuation included (stored codes are not format-validated), keeps its own pair key; and a scheduled purge (`RecipientAccessGuardPurge`, daily, scheduled idempotently by a setup script) deletes guard rows with no active lock that were last touched more than one day ago. Discarded: Platform Cache counters (no cache capacity guaranteed in this org); a cap on pairs per shipment (an overflow bucket would lock or leak).
- S3 → P4: version `force-app/main/default/settings/Security.settings-meta.xml` holding only `sessionSettings.enableMFADirectUILoginOptIn = true` (never a copied full file: `<networkAccess/>` would wipe IP ranges), deploy it, and add `scripts/checks/org-security-check.sh` that fails unless the source file, the org's retrieved Security settings and the Health Check row "Require MFA for all direct UI logins" (MEETS_STANDARD) all agree; it reports the "MFA Enabled" row as information. Discarded: leaving it to production auto-enforcement (X10); fixing every Health Check item now (Medium items stay in the report).
- S4 → P1: `scripts/checks/secret-scan.sh` (shapes: the EntregaYa key shape written so the pattern never matches itself, PEM private-key headers, SFDX auth URLs, `consumerSecret`/password assignments with a value) printing file:line and rule, never the value, exit non-zero; run from `.husky/pre-commit` on staged files (enabled by `npm install` through husky), and runnable over the tracked tree; a self-test script builds fixtures at runtime in a temporary repository. Discarded: `core.hooksPath .githooks` (turns off lint-staged, and husky resets it); rewriting history (force-push, owner).
- S5 → P5: CA-001: block-bodied promise executors. CA-002: drop `SeeAllData=true`; replace the history test with a describe assertion as Ana (Delivery_Instructions__c not accessible) and rely, as recorded in H5, on the platform rule that field history follows FLS plus the existing user-mode refusal test and customer-access-check.sh; remove DEPLOY-ORDER.md step 5c and its mentions. Discarded: deleting the history test without a replacement.
