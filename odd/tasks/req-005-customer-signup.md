## Problems
- P1: Customers cannot create an account or log in to request shipments (evidence: REQ-005 story).
- P2: A guest-callable sign-up creates records and users: mass-assignment (an SObject from the client), injected owner or profile, or bypass of the one-account-per-email rule would let anyone create privileged or duplicate users (evidence: AC-005.2, AC-005.3, X6, X11).
- P3: Login and password reset by email could reveal which emails are registered or allow unlimited password guessing; an unchecked startUrl is an open redirect (evidence: AC-005.5, AC-005.6, X4, X16, X10).
- P4: A customer profile or permission set broader than needed exposes internal fields (credit limit, credit risk) or other customers' records (evidence: BR-03, BR-07, P4, X11).
- P5: Org-specific values (the default record owner's username, global usernames) in versioned metadata break the next org's from-zero deploy (evidence: foundation A11, REQ-004 S4 precedent).
- P6: AC-005.3 itself discloses whether an email is registered; unlimited sign-up attempts would let anyone enumerate customer emails or exhaust the Customer Community licenses (evidence: AC-005.3, X16, licenses 5).

## Solutions
- S1 → P4, P5: access configuration. A custom profile "RutaCargo Customer" (Customer Community license; minimal: no object permissions beyond what the license requires, password policy below) and a permission set `RutaCargo_Customer` (the single actor-specific grant: Account Read and Contact Read/Edit on their own records with FLS on Name, Customer_Type__c, Phone, First/Last name, Email — nothing on Credit_Limit__c, Credit_Risk__c; no Shipment__c yet: REQ-006/007 add it with the sharing set). A ProfilePasswordPolicy for the profile: minimum length 10, complexity "alpha and numeric", lockout after 5 invalid attempts for 15 minutes. A role `RutaCargo_Customer_Owner` (top of a short branch) for the internal owner of customer accounts; `scripts/setup/customer-owner.sh` assigns it to the org's admin (the running user of the setup, never a hard-coded username), sets the site's guest default record owner to that user from a template (like REQ-004's policy template), adds the profile to the network members and enables self-registration with "RutaCargo Customer" as the self-registration profile (the Network metadata references the profile by name; the owner username is the only org-specific value and lives only in the template). guest-access-check section 7 keeps refusing the Visualforce self-registration pages. Discarded: Person Accounts (D5); granting through the profile only (P4: permission sets per actor); the standard "Customer Community User" profile (shared, not least privilege); `username = email` (global collisions).
- S2 → P2, P6: a guest-callable `CustomerSignUpController.signUp(customerType, accountName, firstName, lastName, email, phone, password, confirmPassword)` (`with sharing`, individual fields, non-cacheable) that validates everything server-side (closed list for customerType, lengths of the target fields, email format, phone characters, password policy ≥ 10 with a letter and a digit and `Site.validatePassword`), normalizes the email (trim, lower case) and checks uniqueness against Contact.Email and User.Email of RutaCargo customers through a small `without sharing` helper `CustomerRegistration` (`// SECURITY-JUSTIFICATION`, pending owner approval); a duplicate returns "This email is already registered. Log in instead." with no records created; otherwise the helper inserts the Account (Name, Customer_Type__c; owner set by the platform's default owner rule) and the Contact (first and last name, email, phone), then calls `Site.createExternalUser(user, accountId, password)` with a server-built User (username = normalized email + "." + a stable per-org suffix from `UserInfo.getOrganizationId()` 15-character Id, lower-case; alias, nickname, locale es_MX/en_US per the site, time zone America/Mexico_City, email = normalized email; profile from the self-registration setting, never from the client), all in one transaction with a savepoint: any failure rolls back the Account and Contact and returns a generic message. Discarded: the standard selfRegister component (cannot collect customer type and legal name with these rules); a whole User or Account from the client (X6); a CAPTCHA (no third-party script host is allowed on the site; recorded for Hardening).
- S3 → P3: a guest-callable `CustomerLoginController` (`with sharing`): `login(email, password, startUrl)` resolves the active RutaCargo customer user by normalized email through `CustomerRegistration` (system mode, returns only the username internally) and calls `Site.login(username, password, startUrl)`; an unknown email or a wrong password returns the same "Your email or password is incorrect." (the platform lockout policy of S1 limits guessing); startUrl is accepted only as a site-relative path from a closed list ("/", "/my-shipments", "/request-shipment") else "/"; `forgotPassword(email)` calls `Site.forgotPassword(username)` only when the user exists and always returns the same result, after which the LWC shows the check-email page. Logout: rcHeader shows "Log in" and "Sign up" to guests and "Log out" (the site's `/secur/logout.jsp` under its base path) to logged-in users. Discarded: the standard loginForm (expects the username, which is not the email); a custom password reset token (the platform link is enough and safer).
- S4 → P1: LWCs `rcSignUp`, `rcLogin`, `rcForgotPassword` on the register, login and forgot-password views (replacing the standard components there; the check-email view stays), with client-side validation mirroring the server (password rule, confirmation, required fields, customer type radio), generic server messages shown as text, mobile first, brand palette; Jest with Sa11y.
- S5 → P1: the two seeded customers get active site users (Ana López, Marta Ruiz) through `scripts/setup/seed-customer-users.sh` (idempotent; same username rule and profile; permission set RutaCargo_Customer assigned; no password printed: the platform sends the welcome/reset email, or the owner resets in Setup).
