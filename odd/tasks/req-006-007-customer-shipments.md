## Findings
- REQ-006: the request form asks pickup address, city and postal code; pickup date; recipient name, address, city, postal code, phone and email; service type (Standard, Express); weight; description; declared value; optional order reference and delivery instructions; the price at the current rate (BR-08) is shown before confirming; the pickup date is a business day between the next day and 15 days later; maximum 30 kg and 50,000 MXN declared; on confirmation the shipment is created under the customer, Requested, with its tracking number shown; estimated delivery = pickup date + 5 business days (Standard) or + 2 (Express) (`docs/functional-design.md:141-150`).
- REQ-007: the list shows tracking number, request date, recipient, destination city, status, service type and price, most recent first; filter by status; search by tracking number, recipient or reference; a detail page with the entered data, the price and the current status (`docs/functional-design.md:152-158`).

## Problems
- P1: Customers cannot request pickups online nor follow their shipments (evidence: REQ-006, REQ-007 stories).
- P2: If price, account, status or estimated date come from the client — or from a direct UI API create — a customer can set their own price, put a shipment under another account, or start it in another status (evidence: BR-08, BR-07, BR-09, X6).
- P3: A customer reading another customer's shipments, or any customer reading cost, margin, notes, the hash or credit fields, breaks BR-07 and BR-03 (evidence: BR-03, BR-07, P4, X11).
- P4: Wrong date arithmetic (server clock vs Mexico City, weekends) gives invalid pickup dates or wrong estimates (evidence: AC-006.3, AC-006.6, BR-06).
- P5: The quote shown before confirming may differ from the stored price if computed in two places (evidence: AC-006.2, BR-08).
- P6: Unbounded lists or a search built from client input could be slow or injectable (evidence: AC-007.2, P8, NFR under 2 seconds, 200,000 shipments a year).

## Solutions
- S1 → P2, P4, P5: one pricing and dates service `ShipmentRequestRules` (`with sharing`, pure functions): price = base + per-kg × weight + 1.5% × declared value, rounded half-up to 2 decimals (BR-08); business days = Monday–Friday (no holiday calendar, G1); "today" = the current date in America/Mexico_City (test seam); pickup date valid when it is a business day in [today+1, today+15]; estimate = pickup + 5 or + 2 business days; weight in (0, 30], declared value in [0, 50,000]. Weights with more than 2 decimals are rejected (the field keeps 2; the price is computed on the stored value). The SAME rules are enforced in ShipmentTriggerHandler.beforeInsert, before the existing Original_Estimated_Delivery__c copy, for every insert by a non-internal user (`UserInfo.getUserType() != 'Standard'`, so any external profile that ever receives the grant is covered): Account__c is overwritten with the running user's User.AccountId (one query, no Contact read; the handler's "no SOQL" header is updated), Price__c, Estimated_Delivery__c (and so Original_Estimated_Delivery__c) are computed, Status is Requested (existing), protected fields (Carrier_Cost__c, Internal_Notes__c, Proof_Id__c, Delivered_At__c, Last_*, Reschedule_Count__c, the hash) are cleared, and a rule violation adds a field error — so a direct UI API create obeys BR-07/08/09 exactly like the controller. Discarded: computing only in the controller (UI API bypass, X6); no Create permission plus a system-mode insert helper (keeps user mode out, needs a `without sharing` class for a non-guest actor); a holiday Custom Metadata list (no source for holidays in the design; G1).
- S2 → P3: access configuration for customers, in two steps so Create never exists without the trigger guard. T1: RutaCargo_Customer gets Shipment__c Read and read FLS on the AC-007 list and detail fields (Status__c, Service_Type__c, Price__c, Estimated_Delivery__c, Pickup_*, Origin_City__c, Destination_City__c, Destination_Postal_Code__c, Recipient_Name__c, Package_Description__c, Weight_Kg__c, Declared_Value__c, Customer_Reference__c, Last_Location__c, Last_Update__c); a sharing set "RutaCargo Customer Shipments" (sharingSets/RutaCargo_Customer_Shipments.sharingSet-meta.xml: object Shipment__c, objectField Account__c, userField Account, accessLevel Read, profile "RutaCargo Customer"). T2, in the same commit as the trigger guard: Shipment__c Create and edit (create) FLS only on the AC-006.1 entered fields (which, by FLS rules, also makes Recipient_Address__c, Recipient_Phone__c, Recipient_Email__c and Delivery_Instructions__c readable through the API for the customer's own shipments; G7), and class access to ShipmentRequestController and MyShipmentsController only. Nothing on Carrier_Cost__c, Margin__c, Internal_Notes__c, Delivery_Access_Code_Hash__c, Proof_Id__c, Account Credit_Limit__c / Credit_Risk__c, no Edit/Delete/View All/Modify All. Account: no grant unless T2 (where Create arrives) proves a user-mode insert by a customer user with the required Account__c lookup is refused without it (INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITY); then Account Read with no FLS on Credit_Limit__c / Credit_Risk__c (G2). Discarded: Customer Community Plus roles and sharing rules (license D5); View All (BR-07); Create before the guard (X6 window).
- S3 → P1, P2: `ShipmentRequestController` (`with sharing`, user mode, individual fields): `getQuote(serviceType, weightKg, declaredValue)` (cacheable=false; returns price and the allowed pickup date range), `submitRequest(…all AC-006.1 fields…)` validates with ShipmentRequestRules, never sets Price__c, Estimated_Delivery__c, Account__c or Status__c itself (the trigger computes them; the customer has no FLS on them), inserts in user mode through `DeliveryAccessCode.insertWithCodes` and returns trackingNumber, price, estimatedDelivery and the clear access code (shown once, A1); errors as generic field messages; the price returned equals the stored one (same function). Discarded: deserializing a Shipment__c from the client (X6).
- S4 → P3, P6: `MyShipmentsController` (`with sharing`, user mode, cacheable=false): `listShipments(String status, String searchTerm)` with status from the closed picklist list (or blank), search term trimmed, ≤ 50 characters, escaped and bound (LIKE on Name, Recipient_Name__c, Customer_Reference__c), with an explicit `Account__c = :runningUserAccountId` filter on top of sharing (defense in depth), ORDER BY CreatedDate DESC, LIMIT 200 (G3), returning a DTO with the seven AC-007.1 fields (request date in Mexico City); `getShipment(String trackingNumber)` returns the AC-007.3 DTO for a shipment the user can read (user mode plus the same Account__c filter: another customer's number returns "not found", never an error that leaks existence); per BR-02 (G7) the detail DTO carries the recipient's name, destination city and postal code but not the recipient's address, phone, email or the delivery instructions. Discarded: dynamic sort fields (closed list not needed: one fixed order); Id-based detail URLs (tracking number is the customer's key).
- S5 → P1: LWCs `rcRequestShipment` (form, live quote, confirmation with tracking number, estimate and access code), `rcMyShipments` (list with status filter and search, mobile cards) and `rcShipmentDetail`, on new LWR routes "request-shipment", "my-shipments" and "shipment-detail" (?tracking=RC…), each requiring login through its route content.json `pageAccess` set to the login-required value (today every route is "UseParent"); header links for logged-in customers. Jest with Sa11y; brand palette.
