## Findings
- REQ-002: from a tracking result the recipient enters the destination postal code to open the details (recipient name, delivery address, contact phone, estimated date, delivery instructions); mismatch → "The details do not match this shipment"; Delivered → "Download proof of delivery" fetches the PDF from EntregaYa, never stored in Salesforce; EntregaYa down → "We could not get the proof of delivery, please try again later" (`docs/functional-design.md:101-109`).
- REQ-003: from the details, choose a new date and edit the instructions; the date is between the next day and 7 calendar days after the original estimated date; only Picked up or In transit; at most 2 reschedules; on save the new date is shown and agents see when each change was made (`docs/functional-design.md:111-119`).
- BR-02: the recipient's personal data, the proof and changes to the delivery are exclusive to the recipient; BR-06 Mexico City time; BR-03 price/cost/notes never on the site (`docs/functional-design.md:166-171`).
- Owner decision D1 (.mem/memory.md): recipient access = random delivery access code (hashed, printed on the label/QR) + destination postal code + rate limit of failed attempts, because the policy forbids authorizing a guest by the postal code alone (X16) and tracking numbers are sequential (BR-05). D3: Named Credential + External Credential, key entered by hand (README), no mock URL: tests use HttpCalloutMock; the live download is pending for the owner. D4: the reschedule window is measured from Original_Estimated_Delivery__c (first estimate); field history on the date and the instructions.
- `DeliveryAccessCode.verify(Id, code)` is `with sharing` and reads the hash `WITH SYSTEM_MODE`; a guest has no record access, so verify returns false for a guest caller; `DeliveryAccessCode.matches(Shipment__c, String)` is public and does the constant-time comparison given a row with the hash; verify costs 1 SOQL and ~8 ms CPU; its comment requires external callers to rate-limit (`force-app/main/default/classes/DeliveryAccessCode.cls:170-210`, foundation notes in .mem).
- Shipment__c: Private internal and external, enableHistory true (`force-app/main/default/objects/Shipment__c/Shipment__c.object-meta.xml:14-19`); Estimated_Delivery__c and Delivery_Instructions__c have trackHistory true; Delivery_Instructions__c is LongTextArea(1000); Destination_Postal_Code__c Text(10); Proof_Id__c Text(100); Reschedule_Count__c Number(2,0); the trigger keeps Original_Estimated_Delivery__c as the first estimate (`force-app/main/default/classes/ShipmentTriggerHandler.cls:36,83-91`).
- Support agents can edit Proof_Id__c, Reschedule_Count__c, Estimated_Delivery__c and Delivery_Instructions__c (BR-09 corrections) (`force-app/main/default/permissionsets/RutaCargo_Support_Agent.permissionset-meta.xml`); so Proof_Id__c is not proof that a PDF belongs to the shipment.
- REQ-001 (in progress, odd/tasks/req-001-public-tracking.md) adds the guest-callable PublicTrackingController, the rcTracking LWC with result cards on the home page, and an exact guest class allow-list in scripts/checks/guest-access-check.sh; the guest profile has 0 object permissions; enableApexCDNCaching is true.
- The EntregaYa proof API: GET {base}/proofs/{proofId}, Authorization: Bearer {key}, 200 `{proofId, trackingNumber, signedBy, fileName, pdfBase64}`, 401/404/5xx, 10-second timeout recommended; base URL in the ticket is a placeholder (`docs/functional-design.md:180-189`). The original key is in git history and must be rotated (owner).
- Apex forbids a callout after uncommitted DML in the same transaction.
- Seeded data: 120 shipments with clear codes in the git-ignored .seed-output/access-codes.csv (never reissue again); A6 forbids inserting Shipment__c outside tests; updating a seeded shipment for a live check is allowed (REQ-004 precedent).
- Field history rows are not created inside Apex tests; AC-003.5's "agent sees when each change was made" needs a live check.

## Problems
- P1: Recipients call the contact center to learn delivery details and to change the date (evidence: REQ-002, REQ-003 stories).
- P2: Authorizing by tracking number and postal code alone is guessable (sequential numbers, public postal codes); unlimited attempts would let an attacker brute-force the access code; different messages or timings for "unknown shipment", "wrong postal code" and "wrong code" enable enumeration (evidence: BR-02, X16, D1).
- P3: The guest has no record access; a system-mode read or write reachable anonymously can leak private fields (price, cost, notes, account, hash) or change fields other than date, instructions and counter, or be driven by a record Id the caller chooses (evidence: BR-02, BR-03, P1, P10, X5, X6).
- P4: The proof callout handles a secret API key; the Proof_Id__c is agent-editable, so it could point to another shipment's proof; a malicious proofId could alter the request path; a huge or non-PDF response could exhaust the heap or deliver something else; EntregaYa may be slow or down (evidence: AC-002.4, AC-002.5, P2, X7, NFR "under 10 seconds").
- P5: A reschedule outside the window, in another status, beyond 2 times, or computed with the wrong "today" (server clock vs Mexico City) breaks AC-003.2-AC-003.4 and BR-06 (evidence: AC-003.2-AC-003.4).
- P6: Agents must see each change (AC-003.5); a change made in system mode must still be attributed and timestamped (evidence: AC-003.5).

## Solutions
- S1 → P2, P3: a `without sharing` helper `RecipientAccess` (`// SECURITY-JUSTIFICATION`, pending owner approval) that, given a tracking number, a postal code and an access code (individual fields), reads the shipment `WITH SYSTEM_MODE` by Name (no row lock on Shipment__c), reads its guard row (below), refuses when the guard's Locked_Until__c is in the future (no verification work), compares the postal code (trimmed, case-insensitive, spaces removed) and ALWAYS runs `DeliveryAccessCode.matches` once (constant time; an unknown tracking number or a wrong postal code is checked against the decoy so every failure costs the same hash work). Attempt counters live OFF Shipment__c, in a new internal object `Recipient_Access_Guard__c` (OWD Private, no permission set or profile grants: admins only; Lookup Shipment__c, Shipment_Key__c Text(18) External ID Unique holding the shipment Id and written by upsert on it — a Lookup cannot be unique —, Failed_Attempts__c Number(2,0), Locked_Until__c DateTime), so a failure never changes Shipment__c (no LastModifiedBy noise, no row-lock contention with the EntregaYa POST). Only failures where the postal code matched but the code did not are counted (an attempt with a wrong postal code can never succeed, so it needs no budget; locking a shipment then requires knowing its postal code): the guard row is created or locked `FOR UPDATE`, the counter incremented, and at 5 consecutive counted failures Locked_Until__c = now + 15 minutes; the counter stays at 5 (T1 fix, CODE-001: countFailure re-checks Locked_Until__c on the FOR UPDATE row and does not count while locked), so after the lock expires one more failure locks again until a success resets the counter to 0. Verification failures and the lockout are RETURNED as a result object (outcome + message), never thrown, so the counter DML commits; the controller maps them to its response without throwing after the DML. Every failure — unknown tracking number, wrong postal code, wrong or malformed code — returns the same outcome and message "The details do not match this shipment"; a locked shipment returns "Too many attempts. Please try again in 15 minutes." Discarded: postal code alone (X16); counters on Shipment__c (guest DML on the shipment, lock contention with REQ-004, LastModifiedBy noise); counting every failure (anyone could lock every shipment by sequential number, BR-05); a signed session token (needs an HMAC key stored in the org, A8); Platform Cache counters (capacity not guaranteed in the org, lost on eviction); per-IP limits (the guest's IP is not reliable in Apex); throwing AuraHandledException on failure (rolls back the counter).
- S2 → P1, P3, P5, P6: an entry-point class `RecipientDeliveryController` (`with sharing`, non-cacheable `@AuraEnabled`), every method taking trackingNumber, postalCode and accessCode as individual fields and re-verifying through RecipientAccess on every call (stateless; the LWC keeps the code only in memory):
  - `getDeliveryDetails` → DTO with exactly recipientName, deliveryAddress, contactPhone, estimatedDelivery (ISO), deliveryInstructions, status, canReschedule, reschedulesLeft, rescheduleFrom, rescheduleTo (ISO dates, Mexico City), proofAvailable (Delivered and Proof_Id__c present); no Id, price, cost, notes, account or hash.
  - `rescheduleDelivery(…, String newDate, String instructions)` → validates status in {Picked up, In transit}, Reschedule_Count__c (null = 0) < 2, Original_Estimated_Delivery__c present (null → not reschedulable: canReschedule false; the trigger always fills it from the estimate, so null means no estimate), newDate ISO and between today+1 in America/Mexico_City and Original_Estimated_Delivery__c + 7, instructions ≤ 1000 characters (blank allowed: clears them); locks the shipment `FOR UPDATE` only for this write and updates only Estimated_Delivery__c, Delivery_Instructions__c and Reschedule_Count__c (+1) through RecipientAccess in system mode; returns the refreshed details. A save always carries a new date and counts as one reschedule. Rejections are returned (not thrown) with generic messages from a closed list (outside the window, not reschedulable in this status, limit reached), never exception text; unexpected exceptions become a generic AuraHandledException.
  - Field history on Estimated_Delivery__c and Delivery_Instructions__c (already enabled) records each change with its time and author; agents see it through the "Shipment History" related list, added to the Shipment__c page layout (retrieved first: the org layout has no related lists); a live check script proves rows are written on one seeded shipment.
  Discarded: guest Edit permission with a guest sharing rule (P3; project rule "guest receives no object permissions"); accepting a record Id from the client (X5); a separate "edit instructions only" action (not in the design; it would bypass the 2-change limit).
- S3 → P4: proof of delivery through an External Credential `EntregaYa` (custom authentication protocol, one named principal whose parameter holds the API key, entered by hand in Setup — never in the repository; the `Authorization: Bearer …` header is an AuthHeader parameter of the External Credential built from that principal parameter) and a Named Credential `EntregaYa_API` (URL placeholder `https://entregaya.invalid`, replaced by the owner with the real base URL). Principal access for the site guest user goes through a dedicated permission set `RutaCargo_Guest_Proof_Download` holding ONLY the external credential principal access (profiles cannot hold it: Profile metadata has no externalCredentialPrincipalAccesses; PermissionSet has it since API 59), assigned to the guest user by `scripts/setup/guest-proof-access.sh` (the assignment is data, as in REQ-001 C8) and recorded in DEPLOY-ORDER.md; guest-access-check.sh allows exactly that permission set on the guest, with 0 object permissions. If the platform also requires an object permission (for example on UserExternalCredential) for the guest, the worker stops and returns: that would break "the guest receives no object permissions". `ProofOfDeliveryService` (`with sharing`) does `GET callout:EntregaYa_API/proofs/{proofId}` with a 10-second timeout after validating proofId against `^[A-Za-z0-9_-]{1,100}$` and URL-encoding it; it rejects a response body longer than 2,500,000 characters BEFORE parsing (≈1.8 MB PDF; the 6 MB heap cannot hold a larger base64 body, its parsed copy and the decoded Blob, and a LimitException cannot be caught), and accepts the response only when the status is 200, trackingNumber equals the shipment's Name and pdfBase64 decodes to bytes starting with `%PDF-`; it returns fileName (sanitized to `[A-Za-z0-9._-]`, default `proof-of-delivery.pdf`), signedBy and pdfBase64 to the controller method `downloadProof`, which verifies access first exactly like the other methods: a FAILED check is counted (guard DML) and returned with no callout; only a SUCCESSFUL check is lock-free and DML-free before the callout (no lock is held during the 10-second callout, so EntregaYa's status POST and agent edits are not blocked), and a non-zero attempt counter is reset after the callout, locking only the guard row. Every failure (401, 404, 5xx, timeout, mismatch, invalid PDF) returns "We could not get the proof of delivery, please try again later" and is never logged with the key. Nothing is stored. Discarded: storing the PDF as a File (AC-002.4); the key in Custom Metadata or a Custom Setting (P2); a Remote Site Setting with the key in code (P2).
- S4 → P1: an LWC `rcDeliveryDetails` opened from each rcTracking result card ("Delivery details"), with postal code and access code inputs (code shown grouped XXXX-XXXX-XXXX), the details, "Download proof of delivery" when proofAvailable (builds a Blob from the base64 and downloads it; nothing persisted), and a reschedule form (date input bounded by rescheduleFrom/rescheduleTo, instructions textarea, remaining reschedules) shown only when canReschedule; the saved date is shown on success. Text only, no HTML injection sinks; Sa11y in Jest. Discarded: a separate site page with the code in the URL (the code would leak to history, logs and referrers).

## Assumptions
- E1 (D1, X16): lockout is per shipment: 5 consecutive counted failures (right postal code, wrong code) lock it for 15 minutes. Because only postal-matched failures count, locking a shipment requires knowing its destination postal code; with sequential numbers (BR-05) and guessable postal codes, an attacker who also knows or guesses postal codes could still keep many shipments locked (5 requests per shipment per 15 minutes). Counting only postal-matched failures also lets an attacker learn that a postal code matches (the extra guard DML and its timing, and the lock message after 5 attempts), so "requires knowing the postal code" is a weak barrier and the postal code is not a secret. Accepted: no data is exposed (the 12-character code still guards the details) and the contact center can still help; recorded for Hardening as a fleet-wide DoS and postal-code oracle risk.
