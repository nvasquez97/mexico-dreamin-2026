## Findings
- The contract: one POST per status change with trackingNumber, status, location, timestamp (ISO-8601 with offset) and proofId (null unless delivered); about 5,000 updates a day (`docs/functional-design.md`, "Status changes (EntregaYa calls Salesforce)").
- Owner decision D2 (.mem/memory.md): Apex REST `POST /services/apexrest/entregaya/v1/status`, OAuth 2.0 client credentials through an External Client App, a dedicated integration user (Salesforce Integration license) with a minimal permission set; responses 200 `{"result":"updated"}`, 200 `{"result":"ignored"}` for stale updates, 404 for an unknown tracking number, 400 for an invalid status or body.
- In the org: profile "Minimum Access - API Only Integrations" has PermissionsApexRestServices = false; the "Salesforce API Integration" permission set license exists (1 total, 0 used) and is required for custom object access with the Salesforce Integration user license (plan review, 2026-11-17).
- The External Client App's client-credentials execution user is stored as a username in its OAuth policies metadata, and usernames differ per org (plan review).
- Shipment__c is Private internally (foundation S1); the integration user needs record access through sharing, like the support agents (`force-app/main/default/sharingRules/Shipment__c.sharingRules-meta.xml`).
- Status picklist API names equal the labels EntregaYa sends ("Out for delivery") (`force-app/main/default/objects/Shipment__c/fields/Status__c.field-meta.xml`).
- Tracking numbers are the record Name, `^RC\d{9}$`, indexed (foundation AC-F.2).
- At API 67 Apex DML/SOQL default to user mode, so the integration user's FLS and sharing apply (foundation T1 evidence).
- The site's guest and customers must never reach this endpoint (BR-04); Apex REST is reachable only by authenticated users with class access and the API Enabled / Apex REST Services permissions; class access is not enforced inside runAs tests, so a server-side caller check is needed to prove BR-04 in Apex.
- Foundation lessons (odd/tasks/archive/2026-11-17-foundation.md): criteria-based sharing rules are not evaluated in Apex tests (A10: mirror them with Manual group shares in tests, prove the real rule shares with a script); every check script must fail on a failed query; agents can edit Status__c, Last_Location__c, Last_Update__c, Delivered_At__c and Proof_Id__c (BR-09 allows RutaCargo to correct statuses); licenses: Salesforce Integration 0/1 used, Salesforce Platform 0/3.
- Only 120 seeded shipments exist; A6 forbids stray Shipment__c inserts outside tests; the live check of AC-004.6 updates one seeded "In transit" shipment, which keeps every status present per customer (scripts/seed/verify.sh must stay green).

## Problems
- P1: Without an inbound service, statuses keep being typed by hand hours late (evidence: REQ-004 story).
- P2: Status changes can arrive out of order or be retried; applying an older one would move a shipment backwards; a far-future timestamp would freeze a shipment because every later update would look stale (evidence: AC-004.4).
- P3: A malformed body, an unknown tracking number or a status outside the picklist could corrupt data or leak internals (stack traces, field names) to the caller (evidence: AC-004.3, policy X7; X6 mass assignment if the body were deserialized into an SObject).
- P4: Anyone other than EntregaYa able to call the service, or the integration user having more access than the five status fields, breaks BR-04 and least privilege; RutaCargo agents must keep their own right to correct statuses by hand (BR-09) without becoming able to call the EntregaYa service (evidence: BR-04, BR-09, policy "Inbound services authenticate with OAuth", minimal permission sets).
- P5: The OAuth client secret is a secret: it must never be in the repository; an org-specific username in versioned metadata breaks the next org's from-zero deploy (evidence: policy "No secrets in the repository", foundation A11).
- P6: Two concurrent updates for the same shipment could interleave and keep the older one; the row lock can time out (UNABLE_TO_LOCK_ROW) or a DML/trigger error can occur, and EntregaYa needs a retryable answer without internals (evidence: AC-004.4, 5,000 updates a day, X7).

## Solutions
- S1 → P2, P3, P6: a `with sharing` service class EntregaYaStatusService that receives individual fields (a typed request DTO, never an SObject), validates them (tracking number format, status in the closed list of the six picklist values with exact case, location 1–255 characters, ISO-8601 timestamp with offset and not more than 10 minutes ahead of the server clock, proofId required for Delivered), locks the shipment with `FOR UPDATE`, ignores the update when Last_Update__c is set and the timestamp is not newer, and otherwise updates Status__c, Last_Location__c, Last_Update__c and, for Delivered, Delivered_At__c and Proof_Id__c — all in user mode. Lock timeouts and unexpected DML errors become a typed "retryable" or "internal" outcome. Discarded: a Flow or Platform Event subscriber (cannot return synchronous 404/400); last-write-wins (breaks AC-004.4).
- S2 → P1, P3, P4, P6: a thin Apex REST resource EntregaYaStatusResource (`/entregaya/v1/status`, POST only) that first checks the custom permission RutaCargo_EntregaYa_Sender (403 FORBIDDEN otherwise), parses the JSON body into the DTO, calls the service and maps outcomes: 200 `{"result":"updated"}` / 200 `{"result":"ignored"}` / 404 TRACKING_NOT_FOUND / 400 with one of INVALID_JSON, MISSING_FIELD, INVALID_TRACKING_NUMBER, INVALID_STATUS, INVALID_LOCATION, INVALID_TIMESTAMP, PROOF_ID_REQUIRED / 503 TEMPORARILY_UNAVAILABLE (lock timeout, retry) / 500 INTERNAL_ERROR; error body `{"error":{"code":"…","message":"…"}}`, never a stack trace or a field API name. Discarded: 409 for stale updates (D2 chose 200 ignored so EntregaYa does not retry).
- S3 → P4: permission set RutaCargo_EntregaYa_Integration: user permissions API Enabled and Apex REST Services only; custom permission RutaCargo_EntregaYa_Sender; Apex class access to EntregaYaStatusResource only; Shipment__c Read and Edit; FLS read and edit on Status__c, Last_Location__c, Last_Update__c, Delivered_At__c, Proof_Id__c (Name is always readable); nothing else. A public group RutaCargo_EntregaYa_Integration and a criteria-based sharing rule giving it Read/Write on all shipments. Agents keep their own status edit rights (BR-09) but never get the custom permission or the class. Discarded: `without sharing` in the service; View All on Shipment__c.
- S4 → P4, P5: an External Client App "EntregaYa Status" (ExternalClientApplication, ExtlClntAppOauthSettings and ExtlClntAppGlobalOauthSettings versioned without any secret) with the client credentials flow, scope `api` only, permitted users "admin approved users are pre-authorized" through the integration permission set, IP restrictions enforced (no relaxation); its OAuth policies file (ExtlClntAppOauthConfigurablePolicies, which carries the execution username) is NOT versioned as a plain file: scripts/setup/templates/ holds a template and scripts/setup/entregaya-integration.sh creates the integration user (profile "Minimum Access - API Only Integrations", Salesforce Integration license), assigns the Salesforce API Integration permission set license and then RutaCargo_EntregaYa_Integration, adds the user to the group, and deploys the policies from the template with the org's username; scripts/setup/DEPLOY-ORDER.md gets the new step. The consumer secret stays in the org and is handed to EntregaYa by the owner (README). scripts/entregaya/simulate-status.sh obtains a token with client credentials read from environment variables and posts. Discarded: a Connected App (External Client Apps are the current model); a versioned policies file with a hard-coded username (breaks the next org); password flows.

## Acceptance
- AC-004.1 — Given an integration user with RutaCargo_EntregaYa_Integration, When EntregaYa POSTs `{"trackingNumber":"RC…","status":"Out for delivery","location":"Monterrey, NL","timestamp":"2026-11-20T10:00:00-06:00","proofId":null}` for an existing shipment, Then the response is 200 `{"result":"updated"}` and the shipment's Status__c is "Out for delivery" and Last_Location__c is "Monterrey, NL"; the same holds for a second input with status "Picked up" and location "Guadalajara, JAL".
  *Mutation:* make the resource return 200 updated without calling the service — observed: 13 tests red, e.g. `Expected: Out for delivery|Monterrey, NL, Actual: Requested|null`
- AC-004.2 — Given that update, When the shipment is read, Then Status__c, Last_Location__c and Last_Update__c (the timestamp as an instant) are saved; Given "Delivered" updates with proofId "PRF-88231" at 2026-11-20T15:30:00-06:00 and with proofId "PRF-90417" at 2026-11-21T09:05:00-06:00 on two shipments, Then each Delivered_At__c equals its timestamp and each Proof_Id__c its proofId; Given a non-Delivered update, Then Delivered_At__c and Proof_Id__c are unchanged.
  *Mutation:* stop saving Proof_Id__c on Delivered — observed: `apply_savesDeliveredAtAndProofId_forTwoDeliveries` got null instead of PRF-88231
- AC-004.3 — Given a POST with an unknown tracking number, Then 404 TRACKING_NOT_FOUND and nothing changes; Given a status outside the six values ("Lost", or "delivered" in another case), Then 400 INVALID_STATUS; Given malformed JSON → 400 INVALID_JSON; a missing field → 400 MISSING_FIELD; a tracking number not matching `^RC\d{9}$` → 400 INVALID_TRACKING_NUMBER; an empty or over-255-character location → 400 INVALID_LOCATION; a timestamp without offset, unparsable, or more than 10 minutes in the future → 400 INVALID_TIMESTAMP; "Delivered" without proofId → 400 PROOF_ID_REQUIRED; and no error body contains a stack trace, an exception type name or a field API name.
  *Mutation:* accept any status string — observed: 2 tests red (the restricted picklist accepted lowercase "delivered"; the exact-case list is the only guard); B9 extra: remove the proofId check → 3 tests red
- AC-004.4 — Given a shipment whose Last_Update__c is 2026-11-20T10:00:00-06:00, When an update with timestamp 2026-11-20T09:00:00-06:00 arrives, Then 200 `{"result":"ignored"}` and nothing changes; When one with exactly the same timestamp arrives, Then it is also ignored; When one with 2026-11-20T11:00:00-06:00 arrives, Then it is applied; Given a shipment with no Last_Update__c, When any valid update arrives, Then it is applied. (The `FOR UPDATE` lock is covered by code review; it cannot be mutation-tested in Apex.)
  *Mutation:* compare with `<` instead of `<=` (equal timestamps applied) — observed: `apply_ignoresTheSameInstant_inTwoNotations` got UPDATED instead of IGNORED
- AC-004.7 (P6, X7) — Given the shipment row is locked (simulated UNABLE_TO_LOCK_ROW through a test seam) or the update throws an unexpected DmlException, When EntregaYa POSTs a valid update, Then the response is 503 TEMPORARILY_UNAVAILABLE (lock) or 500 INTERNAL_ERROR (other) with the generic error body, nothing changes, and the body contains no exception text.
  *Mutation:* let the exception propagate (no mapping) — observed: resource rethrow → NullPointerException reached the caller; service rethrow → 500 instead of 503; fix round: drop the depth check → uncatchable "Maximum stack depth reached"
- AC-004.9 (P4, BR-04; T1 security review CODE-001) — Given a user who holds the custom permission RutaCargo_EntregaYa_Sender (the integration user, who has API Enabled and Edit on the five status fields), When they update a Shipment__c directly (standard API / plain DML, not through EntregaYaStatusService), Then the update is refused with a generic error and nothing changes; When the same change goes through the service, Then it is applied; agents (without the custom permission) still edit statuses by hand (BR-09).
  *Mutation:* remove the trigger check that refuses direct updates by custom-permission holders — observed: 4 tests red in 3 classes, incl. the 251-row bulk (expected 251 refused, got 0)

## Assumptions
- B1: a "Delivered" update without proofId is rejected with 400 PROOF_ID_REQUIRED (AC-004.2 needs the proof id; the conservative choice is not to record a delivery without it).
- B2: equal timestamps are ignored (idempotent retries); only strictly newer updates apply; a shipment without Last_Update__c accepts any valid update.
- B3: status transitions are not otherwise validated (the design only orders updates by time; RutaCargo agents can correct statuses by hand, BR-09).
- B4: the consumer secret is read by the owner in Setup and handed to EntregaYa; the simulation script reads ENTREGAYA_CLIENT_ID / ENTREGAYA_CLIENT_SECRET from the environment.
- B5: a timestamp more than 10 minutes ahead of the Salesforce server clock is rejected (400 INVALID_TIMESTAMP), so a wrong clock at EntregaYa cannot freeze a shipment.
- B6: the External Client App enforces IP restrictions, but no login IP ranges are set for the integration user because EntregaYa has not provided its IP addresses; listed as a pending owner step.
- B8 (T1 review): the org has one Salesforce Integration license and one Salesforce API Integration PSL; T4 must create the integration user and assign the PSL in the same step, and tests reuse that user through TestDataFactory.newOrExistingIntegrationUser.
- B9 (T2 review): a proofId longer than 100 characters (the Proof_Id__c length) or with characters outside letters, digits, hyphen and underscore is rejected with 400 INVALID_PROOF_ID, added to the closed list of error codes; an empty-string proofId counts as present and is rejected (EntregaYa sends null when there is none); ASCII letters only.
- B10 (T3 security review CODE-001): request bodies larger than 16 KB are rejected with 400 INVALID_JSON before parsing; the five-field contract fits far below that, and deeply nested JSON could otherwise raise an uncatchable limit exception.
- B11 (T3 fix round): JSON nested deeper than 20 levels is rejected with 400 INVALID_JSON by a non-recursive JSONParser walk before deserializing, because 8 KB of nesting under the size cap still raised the uncatchable "Maximum stack depth reached"; the five-field contract has depth 1.
- B7: lock timeouts answer 503 so EntregaYa retries; other unexpected errors answer 500 with a generic body.
